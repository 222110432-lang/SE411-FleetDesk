# Presentation and demo guide

## Before presenting

Run `START-WINDOWS.bat` ahead of time, while internet access is available for the first dependency download. After a successful build, later starts only need `cd backend` and `java -jar target/fleetdesk.jar`. Open http://localhost:8080 and keep the server terminal open. Use fictional records for the demonstration.

## Slide 1: architecture

“FleetDesk manages company computers. The React interface sends JSON requests to a Java Spring server. The controller handles the routes and input validation. The service applies rules, such as requiring an assignee for an assigned computer. The repository saves and queries records using JPA. The local demonstration uses a persistent H2 database. The application also has configuration for PostgreSQL. The packaged JAR serves the frontend and backend on the same port.”

Follow the diagram while saying this. Be ready to open `ComputerController.java`, `ComputerService.java`, and `ComputerRepository.java`.

## Slide 2: REST API

“POST adds a computer and returns 201 with a generated UUID. GET with an ID retrieves one record. GET on the collection returns a page, using a zero-based page number and page size. PUT replaces the editable fields of an existing record. DELETE removes it and returns 204. The summary route gives totals across the full inventory. Bad input returns 400, missing records return 404, and duplicate identifiers return 409.”

## Live demo, about five minutes

1. Open **Computers**. Show five records and click **Next**, then **Previous**. Explain that the server returns each page.
2. Click **Add computer**. Use name `Presentation laptop`, tag `PC-DEMO`, serial `SE411-DEMO`, location `Riyadh lab`, purchase date `2026-01-01`, and cost `2500`. Keep Available and IT. Save.
3. Open its details. Copy the **Record ID**. Close the dialog, paste that UUID into **Find by record ID**, and click **Find computer**. Explain why the UUID differs from the asset tag.
4. Edit the computer. Change status to Assigned and enter `Demo team` as the assignee. Save and refresh the browser. Find it again to show persistence.
5. Search by `Presentation` or `PC-DEMO`. Change a status or department filter. Clear the search to return to the full inventory.
6. Show a validation example: attempt to save an Assigned computer without an assignee, then correct it. Avoid adding a second record using the same tag.
7. Delete only the record you created. Look up its UUID again to show the missing-record message.
8. Open **About & team**. If asked, show the JUnit/Mockito tests and the test command.

If `PC-DEMO` already exists from rehearsal, update/delete that fictional record first or use `PC-DEMO-2` with a new serial. Do not delete the normal database just to reset a presentation.

## Code questions to understand

**What changed from Part 1?**
Part 1 kept an array in browser memory. Part 2 reads and writes through HTTP. Spring owns the records, and the database keeps them after a refresh or restart.

**Why controller, service, and repository?**
The controller handles HTTP. The service handles business decisions. The repository handles database access. This separates responsibilities and lets us mock the repository when testing service rules.

**What does dependency injection do here?**
Spring provides the service to the controller and the repository to the service through constructors. Tests can provide Mockito mocks instead.

**What do `@RestController`, `@Service`, and `@Entity` mean?**
They identify an HTTP controller that returns response data, a business service managed by Spring, and an object mapped to a database table.

**How does validation work?**
`@Valid` checks the request record's required fields, sizes, patterns, date, and cost. The service checks rules involving more than one field and checks uniqueness. The database also has unique constraints.

**Why validate on both sides?**
The browser gives quick feedback. The backend is authoritative because someone can call the API without using our form.

**How does pagination work?**
The client sends `page` and `size`. `PageRequest` tells the database query which slice to return. The response also includes total records and total pages, so the client can enable Next and Previous correctly.

**Why use a UUID and an asset tag?**
The UUID is the permanent technical identity generated by the server. The tag is a unique label that people can read and edit. Editing a tag keeps the same UUID.

**What are JUnit and Mockito doing?**
JUnit runs tests and assertions. Mockito replaces dependencies so a service test can check one business rule without a real database. Integration tests then exercise the complete backend with a real test database.

**Why does the test suite select Mockito's subclass mock maker?**
The tests mock interfaces and a non-final service. Subclass mocks cover those cases without requiring the JVM to attach an agent while the tests run.

**What does `@Transactional` do?**
It groups a write operation into a database transaction. An unsuccessful operation rolls back rather than leaving a partial change.

**Why `BigDecimal` for cost?**
It represents decimal money amounts without binary floating-point rounding in stored values and backend totals.

**How do you stop duplicate identifiers?**
The service normalizes the text and checks for duplicates. Unique database constraints protect against simultaneous requests that pass the check at the same time.

**How does the UI handle a failed request?**
It displays a message. Failed saves retain form data. Failed deletions keep the confirmation open. Inventory loading has a Retry button. An older search response cannot overwrite a newer result.

**Does it follow Twelve-Factor?**
It uses environment configuration, declared dependencies, separate build/run steps, port binding, process-output logs, and stateless API logic. The external PostgreSQL setup supports separating storage from the app. The local H2 demo and startup migrations leave some factors only partly addressed. See `twelve-factor.md`.

**Did you use AI?**
“AI tools assisted with setup, implementation, and testing.” Explain the code you understand and describe your own work accurately.

**Is this ready for real public company data?**
It is a local course demonstration. A production deployment would need authentication, authorization, backups, and deployment-specific checks.
